# Bing.Offices 文档自动化方案设计

> 版本 1.0 · 2026-09-19
> 配套实现：[`tools/docgen/`](../../tools/docgen/README.md)

> **本轮交付范围：** 文档生成工具、说明文档与配置。CI 工作流和 commit-lint 不属于本轮交付。
> `docs/generated/` 与 `artifacts/docs/` 下生成的文档和图片均为本地生成物，不纳入 Git。
> 下文保留的架构方案、历史设计及验证数字仅作背景，不代表本轮验收结论；历史记录不证明相关产物当前可重建。

## 1. 背景与现状盘点

### 1.1 问题：数据齐备，文档缺席

本仓库的工程活动已经产生了大量**结构化、可机读**的产物，但它们只停留在「原始文件」形态，没有被组织成任何人愿意读的文档：

| 已有原始产物 | 当前体量（实测） | 现状 |
|---|---|---|
| `TestResults/*.trx` | 5 个文件 / **1060 个用例** / 通过率 **99.81%** | 埋在仓库根目录，无人汇总 |
| `BenchmarkDotNet.Artifacts/results/*.csv` | **6 组基准 / 38 个方法** | 只有 BDN 自带的 github.md 快照，无趋势、无口径统一 |
| `output/release/*.xml` | 3 个程序集 / Npoi 单程序集 **499 个成员**注释 | 只有跳转到源码才能看 |
| `build/api-snapshot-baseline.json` | schema `bing.offices.public-api.v2` / **1017 个公共成员** | 仅用于 CI 校验，不产出给人看的文档 |
| `git log` | **120 次提交** / 规范符合率 **76.7%** | 无 CHANGELOG，发布靠回忆 |
| `.github/workflows/ci.yml` | 11 个步骤 | 只做 build / test / pack，**不产出任何文档** |
| `docs/*.md` | 22 个文件 | 全手写，与源码无同步机制，存在腐化风险 |

**核心矛盾：** 数据的生产成本已经付过了，文档的组装成本却要在每次汇报、每次发布时重复支付。而且手工组装必然滞后与失真。

### 1.2 现状暴露出的三个具体问题

1. **质量证据无法直接引用。** `TestResults` 里有 2 个失败用例（`PublicApiContractTest` 的 API 快照比对，失败原因 `BLOCKED: API baseline approvedBy is empty.`），但没有任何一份文档会把「通过率 99.81%、2 个失败、失败原因」摆到评审桌面上。
2. **性能结论不可比较。** 38 个基准方法散落在 6 份 CSV 里，口径（Job / Runtime / RowCount）未统一，无法回答「这次改动是否引入性能回归」。
3. **发布说明全靠人工。** 提交规范符合率只有 76.7%，意味着即使手工写 CHANGELOG，也有近四分之一的提交无法被正确归类。

### 1.3 目标与非目标

**目标**

- 把上述原始产物**自动组装**为四类文档，覆盖技术读者、管理者与开源使用者。
- 一套数据源，多种输出格式（Markdown / DOCX / XLSX / PPTX），**同一份内容不必重复编写**。
- 生成物可被 CI 校验，把「文档是否与代码同步」变成可失败的门禁。
- 品牌与排版单点定义，改一处即可全量换肤。

**非目标**

- 不做富文本 WYSIWYG 编辑，不做在线协作文档。
- 不做 Word / PDF 的人工精排（复杂图文混排仍建议人工把关）。
- 不让流程读取或上传任何外部系统数据；输入只来自本仓库。

## 2. 总体架构

### 2.1 三层结构

```
┌──────────────────────────────────────────────────────────────────────┐
│ 数据源（已存在的原始产物，零改动）                                     │
│  .trx   BDN CSV   XML 注释   API 快照   git log   （未来：coverage）   │
└────────────────────────────┬─────────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ① 采集层  collectors/                                                │
│    只做「原始格式 → 纯数据对象」，不构造文档、不接触渲染               │
│      tests.py      → TestRun[] / TestCase[]                          │
│      benchmark.py  → BenchmarkSet[] / BenchmarkRow[]                 │
│      api.py        → ApiInventory / AssemblyApi / ApiMemberDoc       │
│      changelog.py  → ChangeLog / ChangeEntry[]                       │
└────────────────────────────┬─────────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ② 组装层  reports.py  +  中间模型  model.py                          │
│    把纯数据编排成与输出格式无关的 Document                            │
│      Document { 元信息, 摘要, 关键结论, Section[] }                   │
│      Section  { title, level, Block[] }                              │
│      Block    = Para | Bullets | Table | Chart | Metrics |           │
│                 Note | Code | PageBreak                              │
│    ★ 全系统唯一的格式无关表达层                                       │
└────────────────────────────┬─────────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ③ 渲染层  renderers/                                                 │
│    只消费 Document，不感知数据来源                                    │
│      markdown.py   → .md    （本地生成，不入 Git）                    │
│      docx.py       → .docx  （正式文档：封面 + 目录域 + 页眉页脚）      │
│      xlsx.py       → .xlsx  （可分析台账 + Office 原生图表）           │
│      pptx.py       → .pptx  （汇报材料 + Office 原生图表）             │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 为什么是「采集 / 组装 / 渲染」三层

这是整个方案最重要的一个决策。如果按「一种文档一个脚本」来实现，会立刻陷入组合爆炸：4 类文档 × 4 种格式 = 16 条路径，每加一种格式就要改 4 处，每加一类文档又要改 4 处。

引入 **`Document` 中间模型**后，两条扩展轴彻底解耦：

| 想做 | 需要改的地方 | 不需要改的地方 |
|---|---|---|
| 新增输出格式（如 PDF） | `renderers/` 加一个文件 + 注册 | 所有采集器、所有报表 |
| 新增文档类型（如合规报告） | `reports.py` 加一个 builder + 注册 | 所有采集器、所有渲染器 |
| 接入新数据源（如 coverage） | `collectors/` 加一个解析器 | 所有渲染器、所有报表 |
| 换品牌配色字体 | `theme.py` | 全部渲染代码 |

这是「可复用模板」原则的结构化落地：**模板不是一堆 `.docx` 样板文件，而是中间模型本身。**

### 2.3 一个必须存在的约束：生成前自检

`Document.validate()` 在渲染前检查结构一致性，例如：

- 表格每行单元格数是否与表头一致；
- 图表每个系列的值个数是否与类别数一致；
- 章节层级是否合法。

这不是防呆，而是防**静默劣化**：一张 9 列表头配 8 列数据的表，在 Word 里不会报错，只会看起来不对。让它在生成前失败，比让人去肉眼看 40 页文档可靠得多。本地 `--check` 可运行这一层；CI 接入仅为历史设计，本轮未交付或启用。

## 3. 数据源 → 文档类型映射

### 3.1 映射矩阵

| 文档类型 | target | 主数据源 | 主要读者 | 主推格式 |
|---|---|---|---|---|
| 测试与基准测试报告 | `tests` | `.trx` + BDN CSV | 内部工程团队、管理层 | DOCX + XLSX |
| 发布说明与变更日志 | `release` | `git log` + API 快照 | 开源社区使用者、工程团队 | Markdown + DOCX |
| 项目进展汇报 | `deck` | 全部数据源 | 管理层与决策者 | PPTX |
| 公共 API 参考 | `api` | XML 注释 + API 快照 | 内部工程团队、开源使用者 | Markdown |

### 3.2 每类文档的组织方式

**① 测试与基准测试报告**（5 章 / 9 表 / 6 图）

```
摘要 + 关键结论
├─ 1 测试执行概览    指标卡（总数/通过/失败/通过率/耗时）+ 逐套件明细表
├─ 2 失败用例明细    失败原因摘要表（含错误首行）+ 危险级别提示
├─ 3 测试分层视图    按测试项目聚合的通过率与健康状态
├─ 4 基准测试结果    极值指标卡 + 每基准类的明细表 + 横向柱状图
└─ 5 结论与风险      人工沉淀的判断性结论（见 §11 边界说明）
```

**② 发布说明与变更日志**（7 章 / 3 表 / 2 图）

```
├─ 1 版本概览        指标卡含「提交规范符合率」，低于 80% 自动转警告色
├─ 2 新增功能        按 scope 聚合
├─ 3 缺陷修复        按 scope 聚合
├─ 4 性能优化与其他  非面向使用者的变更汇总表
├─ 5 公共 API 快照   程序集 × 成员数 × 哈希 × 注释覆盖率
├─ 6 变更分布        类型饼图 + scope 柱状图
└─ 7 升级提示        运行时边界 + 提交规范改进建议
```

**③ 项目进展汇报**（5 章，PPT 优先）

```
├─ 1 项目概览        4 张 KPI 卡
├─ 2 质量指标        套件明细表 + 通过/失败堆叠柱状图
├─ 3 性能表现        最慢 8 个方法（横向柱）+ 最省内存 8 个方法
├─ 4 近期交付        面向使用者的提交清单
└─ 5 风险与下一步    4 条已知风险 + 3 条下一步计划
```

**④ 公共 API 参考**（4 章 / 28 表）

```
├─ 1 程序集清单      程序集 × TFM × 成员数 × 注释覆盖 × 快照哈希
├─ 2 成员种类分布    按构造函数/方法/属性…统计 + 饼图
├─ 3 命名空间与类型  逐个命名空间列出类型名与中文摘要（28 个命名空间）
└─ 4 使用约束        Provider-neutral 契约边界、异步边界、模板流约束
```

### 3.3 覆盖度与缺口

| 需要的文档类型 | 数据源是否就绪 | 状态 |
|---|---|---|
| 工程内部技术文档 | XML 注释 ✅ / API 快照 ✅ | **已覆盖** |
| 测试与基准报告 | TRX ✅ / BDN CSV ✅ | **已覆盖** |
| 发布说明与变更日志 | git ✅ / 快照 ✅ | **已覆盖**（受提交规范制约） |
| 汇报与演示材料 | 上述汇总 ✅ | **已覆盖** |
| 对外交付文档 | 上述 + 品牌主题 ✅ | **已覆盖**（DOCX 模板层） |
| 代码覆盖率报告 | ❌ CI 未产出 Cobertura | **缺口**，见 §10 阶段二 |

## 4. 技术选型

### 4.1 选型结论

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.10+ | 用户指定；生态最成熟；非 .NET 同事也能改 |
| DOCX | `python-docx` | 支持样式、段落、表格、页眉页脚、域（TOC/PAGE） |
| XLSX | `openpyxl` | **支持 Office 原生图表**，产物可在 Excel 里继续分析 |
| PPTX | `python-pptx` | **支持 Office 原生图表**，汇报人可现场改数据 |
| 位图图表 | `matplotlib` | 仅供无原生图表能力的 DOCX / Markdown 使用 |
| Markdown | 纯 Python 字符串拼接 | 无需模板引擎；输出确定、diff 友好 |

部分依赖包含原生扩展，安装时优先使用适配当前 Python 和操作系统的预编译包；没有适配包时可能需要额外构建环境。

### 4.2 一个关键决策：原生图表优先，位图兜底

```
PPTX  ──► Office 原生图表（可编辑、可换数据、可套用报表主题）
XLSX  ──► Office 原生图表
DOCX  ──► matplotlib PNG（Word 无原生图表写入能力）
MD    ──► matplotlib PNG（落到 assets/ 并相对引用）
```

**理由：** 汇报人拿到 PPT 后几乎一定会想改颜色、改排序、加一条数据。如果给的是图片，这些诉求全部变成「请研发重新生成」；给原生图表则是一个拖拽的事。把「可编辑性」作为演示类文档的一等要求，是本方案与「截图式汇报」的核心区别。

### 4.3 为什么不复用现有 .NET 工具链

`build/` 下已有 FlubberCore 构建脚本，技术上可以用 C# 写文档生成。没有这样做的原因：

1. **依赖成本**：DOCX/PPTX/XLSX 在 .NET 侧需要 OpenXML SDK（或付费商业库），而 Python 侧是成熟的开源组合。
2. **修改门槛**：文档模板的调整是高频、低风险的小改动，交给非 .NET 同事用 Python 改的成本远低于 C#。
3. **隔离性**：文档流水线不与产品程序集共享依赖图，避免「改文档工具导致产品构建失败」。

代价是多引入一套 Python 运行时。权衡后认为**收益大于成本**，且通过 `run.py` 自举虚拟环境把环境管理成本压到了「一条命令」。

## 5. 品牌与模板规范

### 5.1 单点主题定义

所有视觉属性集中在 `theme.py` 的 `Theme`：

```python
primary    = "1F4E79"   # 主色：标题、表头、封面背景
accent     = "2E75B6"   # 辅色：分隔线、序号圆点、图表系列一
muted      = "59636E"   # 次要文本：页脚、说明
surface    = "F2F5F9"   # 浅底：指标卡、斑马纹行
success    = "1A7F37"   # 通过 / 健康
danger     = "B3254A"   # 失败 / 阻塞
warning    = "9A6700"   # 警告 / 需关注
font_heading = "微软雅黑"
font_body    = "微软雅黑"
```

**硬约束：渲染代码中不允许出现颜色字面量或字号数字。** 这一条由代码评审保证。换肤只需改上述常量，四类文档 × 四种格式同步生效。

### 5.2 中文排版要点（已实现）

| 要点 | 处理方式 |
|---|---|
| Word 中文回退 | 每个 run 显式设置 `w:rFonts` 的 `ascii / hAnsi / eastAsia / cs` 四个属性，缺一不可 |
| matplotlib 中文 | `font.sans-serif` 按「微软雅黑 → 黑体 → Noto Sans CJK」回退，并关闭 `unicode_minus` |
| Excel 列宽 | 中日韩字符按 2 个宽度计算，避免中文列被截断 |
| 工作表名约束 | 过滤 `\ / * ? : [ ]`，截断到 31 字符，重名自动加后缀 |
| PowerPoint 溢出 | 单页内容块达到底部阈值即停止，超出部分由后续页承载；表格默认只展示前 14 行并显式标注 |

### 5.3 各格式的样式约定

| 格式 | 约定 |
|---|---|
| DOCX | 封面（品牌 + 标题 + 元信息表）+ 摘要 + 关键结论 + **目录域**（打开后 F9 更新）+ 页眉 + 页脚（`PAGE` / `NUMPAGES` 域 + 密级）+ A4 页边距 |
| DOCX 表格 | `Table Grid` 样式 + 表头主色底纹白字 + 斑马纹 + 状态列语义着色 + 数值列右对齐 |
| XLSX | 「概览」页承载元信息与指标卡；每张表独立 Sheet；首行冻结 + 自动筛选；图表独立 Sheet |
| PPTX | 16:9 空白版式 + 手工文本框；顶部品牌色条；页脚统一；封面/目录/节页/图表页/收尾页五类版式 |
| Markdown | 元信息表 + 自动目录锚点 + 表格 + `> **警告**：` 引用块表示提示 + 图表落到 `assets/<文档名>/` |

### 5.4 文档元信息规范

每份文档都带统一的元信息头，便于归档与追溯：

| 字段 | 说明 | 示例 |
|---|---|---|
| `title` / `subtitle` | 标题与副标题 | 测试与基准测试报告 |
| `doc_id` | 文档编号（稳定，不随版本变） | `BO-QR-001` |
| `version` | 从 API 快照的 nupkg 文件名自动提取 | `2.0.0` |
| `generated_at` | 生成时间 | 2026-09-19 10:03 |
| `source_commit` | 数据来源提交（前 12 位） | `dce0fc8d2dfa` |
| `classification` | 密级 | 内部资料 / 公开 |

`source_commit` 记录生成时的 HEAD 提交；测试、基准和 XML 文件可能来自其他版本，未提交的源码也不会由该字段标识。正式交付前需单独核对输入证据与代码版本的一致性。

## 6. 产物清单与目录约定

| 产物 | 路径 | 纳入 Git | 说明 |
|---|---|---|---|
| 生成文档（Markdown 等格式） | `docs/generated/` | 否 | 本地生成；目录内生成文档均不提交 |
| 生成图片与图表资源 | `docs/generated/`、`artifacts/docs/` | 否 | 本地生成；与文档一并排除在 Git 外 |
| DOCX / XLSX / PPTX / PDF 等生成文档 | `artifacts/docs/` | 否 | 本地生成；目录内生成文档均不提交 |

**产物策略：** 生成文档和图片都不纳入 Git。代码评审与版本控制针对生成工具、说明和配置；本轮不提供 CI Artifact 归档。能否重新生成取决于运行时可用的输入数据，历史产物记录本身不构成可重建证据。

## 7. 使用与集成

### 7.1 本地使用

```bash
python tools/docgen/run.py all                      # 全部文档、全部格式
python tools/docgen/run.py tests --format docx,xlsx # 按需
python tools/docgen/run.py all --check              # 只自检
```

`run.py` 自举：首次运行自动创建 `tools/docgen/.venv` 并安装依赖，不需要任何手工准备。

### 7.2 CI 集成（历史设计，未启用）

以下是历史工作流设计：`.github/workflows/docs.yml` 当前未跟踪，且不属于本轮交付；此流程未作为本轮验收或运行结果：

```
Checkout(fetch-depth: 0)   ← 变更日志需要完整历史
  → Setup .NET + Python
  → build（产出 XML 注释）
  → dotnet test --logger trx（产出 TRX）
  → pip install -r tools/docgen/requirements.txt
  → python tools/docgen/run.py all --check    ← 门禁：模型不自洽就失败
  → python tools/docgen/run.py all
  → 校验 16 个产物存在且非空
  → upload-artifact: bing-offices-documents
```

三个历史设计要点：

1. **`fetch-depth: 0`** —— 浅克隆会让 `git log` 拿不到历史，变更日志直接空掉。
2. **`--check` 前置** —— 结构不自洽时快速失败，不浪费渲染时间，也避免把坏文档传成 Artifact。
3. **独立工作流** —— 文档生成失败不应阻塞产品构建；反之亦然。

### 7.3 与既有工作流的衔接

| 既有机制 | 衔接方式 |
|---|---|
| `ci.yml` 的 `artifacts/ci-contracts` | 可作为额外数据源接入，产出「契约一致性」章节 |
| `build/api-snapshot-baseline.json` | 已作为 API 参考与发布说明的数据源 |
| `docs/excel/*.md` 手写文档 | 保留不动；自动生成物集中在 `docs/generated/`，职责不重叠 |

#### 注释覆盖率口径（重要）

```
错误口径：XML 条目里有 summary 的比例 ≈ 100%
          —— 完全没写注释的成员根本不会出现在 XML 文件里

正确口径：覆盖率 = 有 summary 的对外可见成员数
                  / 公共 API 快照记录的对外可见成员数（public + protected）

并且：无参构造函数不计入分母。绝大多数类型的无参构造由编译器生成，
      无法为其编写 XML 注释，计入只会把覆盖率系统性低估
      （实测：计入 92.07% vs 不计入 95.20%；构造函数自身注释率仅 49.4%）。
      构造注释率作为参考值单独输出，不参与判定。
```

#### 文档腐化防护的判定期望

| 场景 | 结果 |
|---|---|
| 改了公共 API，示例没跟着改 | 编译失败（示例在 `Bing.Offices.Docs.Tests` 里必须能编译） |
| 改了示例源码，没重新生成文档 | `docs-check`：「文档示例 X 与源码 Y:Z 不一致，请重新生成文档」→ 退出码 1 |
| 文档里出现了源码中不存在的示例 | `docs-check`：「文档示例 X 在 Docs.Tests 中不存在」→ 退出码 1 |
| 示例引用了不存在的 `Bing.Offices.*` 命名空间 | `docs-check` 报错 → 退出码 1 |

## 10. 风险与限制

| # | 风险 / 限制 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **提交规范符合率偏低**（历史测量记录） | 旧报告中部分提交落入「其他」 | commit-lint 与阈值门禁均为历史设计；CI 未纳入本轮交付或启用 |
| R2 | **覆盖率输入依赖 Cobertura 数据** | 缺少输入时报告无法包含覆盖率维度 | Cobertura 采集与 CI 产出配置为历史设计；本轮未交付 CI 接入 |
| R3 | **无历史基线** | 基准只有当期绝对值，无法判定回归 | 阶段二已实现归档 + 趋势对比 |
| R4 | 结论性文字为预置内容 | 「结论与风险」章节的表述由模板固化，不随数据自动推理 | 明确标注为「人工维护的判断」，不伪装成自动结论 |
| R5 | DOCX / Markdown 图表为位图 | 无法在 Word 里改图 | 需要可编辑图表时使用 XLSX / PPTX 产物 |
| R6 | PPTX 单页内容容量有限 | 超长章节可能溢出 | 已实现内容块阈值截断 + 表格前 14 行截断并标注 |
| R7 | 引入 Python 运行时 | 多一套环境 | `run.py` 自举 + 虚拟环境隔离在仓库目录，不入库 |
| R8 | XL 级数据源渲染慢 | 大表全量写入拖慢生成 | 表格默认行数上限可配置；必要时改抽样 |
| R9 | 生成文档和图片不入库 | Git 中不保留生成物历史版本 | 本轮不提供 CI Artifact 归档；需保留的交付物应由使用方另行归档 |
| R10 | 中文排版依赖系统字体 | Linux CI 上「微软雅黑」缺失会回退 | matplotlib 已配多级回退；Office 文档由 Word 渲染，不受 CI 字体影响；PDF 用 reportlab 内置 CID 字体，同样不依赖系统字体 |
| R11 | **注释覆盖率口径易错** | 用 XML 文件自己当分母会得到 ≈100% 的假覆盖率 | 分母改为公共 API 快照的 public+protected 成员数，并剔除无法注释的无参构造函数；口径在 `gates.py` 文档字符串中固化说明 |
| R12 | PDF 目录页码需多趟构建 | 单趟拿不到真实页码 | 最多 3 趟构建，页码稳定即停；文档规模小，开销可忽略 |

**特别说明（针对 R4）：** 报告中「质量：通过率 99.81%」「性能：6 组基准覆盖…」这类内容是由数据驱动生成的；而「NPOI 为 DOM 模型，MaxInputBytes 不覆盖解压后峰值内存」这类判断来自人工沉淀的项目知识。方案刻意把两者分区呈现 —— **自动生成的数字不冒充专业判断**。
