# 移除生产程序集友元依赖，补齐文件提交扩展点

用户于 2026-09-27 明确要求实施本计划。Task ID：BING-OFFICES-PUBLIC-PROVIDER-BOUNDARY-20260927-001。

## 目标与现状

Core 向 Npoi、ClosedXml 开放内部访问，两个 Provider 的失败工作簿输出有四处直接调用 AtomicFileCommitter。已有公开 IFileExportCommitter / DefaultFileExportCommitter 可复用。当前友元测试错误允许这两个生产程序集。

目标：所有生产程序集仅向精确列出的测试程序集授予内部访问，官方与第三方 Provider 使用相同公开契约。

## P1：统一文件提交与依赖注入

- 删除 Core 对 Npoi、ClosedXml 的两条生产友元声明，保留测试友元。
- 两个导入器持有 IFileExportCommitter，默认使用 DefaultFileExportCommitter；四处内部调用改为接口调用。
- NPOI 同步写入器接收导入器的提交服务，异步调用同一实例的 CommitAsync，避免重复提交。
- DI 解析宿主的 IFileExportCommitter；ClosedXML 继续使用配置的 DOM 准入器。
- 保留 staging、序列化限制、取消、异常观察、流所有权和临时文件清理行为。
- 两个导入器原有五参数构造函数及默认参数保持原样，各新增六参数公开重载，前五项类型和顺序不变，末项 IFileExportCommitter fileExportCommitter；全部必传，null 回退默认实现。
- 内部构造链同时接收提交服务和原有 staging / 准入依赖；不新增接口或公开内部工具。

验收：无生产友元仍可编译；同步、异步文件失败产物均使用指定提交服务，旧构造函数保持兼容。

## P2：边界约束与消费者

- 全部生产项目编译通过；不得反射或复制源码绕过边界。
- 现有第三方 NuGet 消费者验证公开默认提交器、自定义提交器和新增构造重载，接入 net6.0 / net8.0 包验证流程。
