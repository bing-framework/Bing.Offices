# 多透视有界资源矩阵

原始命令、退出码、stdout、嵌入结果和独立产物见 `artifacts/resources/results.json`。六个完整来源/缓存场景及四个取消场景全部退出 0。矩阵在本机独立进程串行执行，时间窗口依据 probe JSON 时间戳为 2026-10-04 21:24:28Z～21:29:22Z；不是容量上限或统计基准。

## 测量范围

工具通过已验证本地 2.0.0 NuGet 包使用 ClosedXML XLSX，运行时为 .NET 8.0.31；取消另覆盖 .NET 6.0.36。每个成功场景检查完整工作表顺序、表头、每一行来源，以及每个缓存的字段和每一条记录，不只检查文件存在或局部汇总。

时间和 GC 托管分配从输入模型构造前开始，到 Provider 文件导出返回结束。峰值工作集在重开验证前读取，是该进程的历史峰值；不包含之后的验证峰值。机器运行时报告 22 个逻辑处理器、约 33.69 GB 可用内存预算；物理机 CIM 信息读取被拒。CPU 仅在所有场景之后采样，最终汇总约 17.66%，不能归因到某个场景。

## 结论与后续

- 当前引擎已对相同有界来源共享缓存，不需要再凭假设实现第二套共享缓存。业务序列也只枚举一次。
- `enumeratedRows` 不统计 DOM 来源预检或缓存内部扫描。当前 Writer 对每个透视调用来源校验，源码可见重复预检；本矩阵没有测量其独立耗时，不能把所有分配增长归因于它。
- 同源四透视 10K 的分配高于单透视，支持在高级透视阶段对来源预检做定向测量，再决定是否复用。若引入缓存，应补范围/配置隔离、命中、未命中和失败后状态职责测试。
- 多来源会增加 DOM、缓存和文件体积；当前结果不证明恒定内存，不适用于不受控并发、不同字段宽度、百万行或部署容器。
- 本阶段没有新增任意性能阈值，没有修改生产缓存算法；来源面积、透视数量、字段宽度及展开预算仍需后续基于业务和部署证据设计。
